## 오늘의 목표

AI가 작성한 코드를 직접 이해하고 수정할 수 있도록 데이터 입력, 상태 소유자, 호출 관계, 저장·로드와 씬 인계, 스킬 실행 흐름을 실제 소스 기준으로 공부합니다. 특히 빗자루 Q 연계의 공유 쿨타임과 다음 타격 대기 시간을 구분하고, 설명을 스크립트에도 한국어 주석으로 남깁니다.

## 작업 내용

### 1. 데이터 로드와 전투 상태 설명

`DokkaebiGrowthDatabase.cs`에 Excel → 변환 도구 → JSON → Unity 데이터 조회 흐름을 상세히 설명했습니다. 조합 단계와 개별 타격 데이터, 최초 로드와 검증, 실패 시 자동 재시도 제한, 캐시와 개체 상태의 차이도 정리했습니다. 자료형과 C# 문법은 해당 코드에서 어떤 역할을 하는지 함께 풀어 썼습니다.

`PrototypeSkillUseController.cs`에는 Q 입력 요청부터 사용 승인·자원 소비·돌진·피해·연출 종료·다음 타격까지의 순서를 설명했습니다. 슬롯 쿨타임, 개체별 공유 쿨타임, 연계 만료 시점이 서로 다른 상태라는 점을 강조했습니다.

### 2. Q1 → Q2 → Q3 실제 호출 순서 리뷰

3타가 해금된 빗자루를 Q 슬롯에 배치하고 자원이 충분한 경우를 기준으로 설명했습니다.

1. `GameplayInputReader`의 Q 입력 콜백이 0번 슬롯 요청을 전달합니다. 입력은 요청이며 곧바로 사용 승인을 의미하지 않습니다.
2. `HandleSkillSlotRequested()`가 슬롯 소유 개체를 찾고 `TryStartBroomChain()`에서 연계 만료, 조합 단계, 현재 타수와 사용 가능 여부를 확인합니다.
3. Q1은 공유 쿨타임을 확인하고 자원을 지불한 뒤 사용을 승인합니다. 이 시점부터 공유 쿨타임 10초와 Q2 대기 시간 6초가 시작됩니다.
4. `Execute()`가 일반 이동을 제어하고 시작 이벤트, 돌진, 타격 시점의 피해 판정과 타격 이벤트, 남은 동작을 순서대로 처리합니다. 검 콜라이더에 닿아서 피해가 발생하는 방식은 아닙니다.
5. 동작이 끝나면 다음 연계 타수로 넘어갑니다. 타격 순간과 동작 종료는 다른 시점입니다.
6. Q2는 공유 쿨타임을 다시 요구하지 않지만 실행 중 동작과 자원 조건은 확인합니다. Q2가 승인되면 Q3 대기 시간이 새로 6초 설정됩니다.
7. Q3가 승인되면 연계 상태는 초기화됩니다. Q3 동작은 계속 실행되고 공유 쿨타임은 유지되므로 즉시 새로운 Q1을 쓸 수 있는 것은 아닙니다.

| 구분 | 시작·갱신 시점 | 종료 후 의미 |
| --- | --- | --- |
| 공유 쿨타임 기본 10초 | Q1 사용 승인 | 다음 연계의 Q1을 다시 승인할 수 있는 시간 조건 |
| Q2 대기 6초 | Q1 사용 승인 | 만료하면 연계만 Q1 상태로 초기화 |
| Q3 대기 6초 | Q2 사용 승인 | 만료하면 연계만 Q1 상태로 초기화 |
| 입력 버퍼 0.18초 | 현재 동작의 종료 직전 구간 | 다음 슬롯 요청 하나를 보관하고 실행 가능 시 처리 |

Q1 이후 Q2 없이 6초가 지나면 연계는 Q1 상태로 돌아가지만, 공유 쿨타임은 4초 남습니다. 입력 버퍼에 요청이 들어간 순간에는 연계 시간이 갱신되지 않고 실제 다음 타격이 승인될 때 갱신됩니다. 자원 부족으로 승인되지 않은 요청도 연계 시간을 갱신하지 않습니다.

위 수치는 기존 기본 데이터와 구현을 설명한 것이며 이번 작업에서 수정하지 않았습니다.

### 4. 상태 소유와 저장·로드의 경계

- 공통 데이터: `DokkaebiGrowthDatabase`와 정의 에셋이 제공합니다.
- 개체별 성장·유대: 실제 파츠 개체의 성장 상태가 보관합니다.
- 배치·키 할당: `PrototypeBlueprintLoadout`이 관리합니다.
- 전투 중 연계·쿨타임: `PrototypeSkillUseController`가 관리합니다.
- 자원·체력: `CoreResourcePool`과 `PrototypeDamageReceiver`가 각각 소유합니다.
- 시각 연출: 이벤트와 실행 상태를 받아 표시하며 피해나 쿨타임을 결정하지 않습니다.

`TutorialSessionTransfer`는 실행 중 메모리로 다음 씬에 상태를 한 번 인계하는 구조입니다. 디스크에 저장하고 게임을 재시작한 뒤 불러오는 저장 시스템이 아닙니다. 인벤토리 → 배치 → 키 할당의 복원 순서와 자원·체력·내구도 보존을 설명했습니다. 현재 스킬 쿨타임과 연계 타이머는 해당 스냅샷으로 전달하지 않습니다.

## 발생한 문제

클래스 이름과 짧은 주석만으로는 입력과 사용 승인, 공통 수치와 실행 중 상태, 타격과 동작 종료, 씬 인계와 영구 저장을 구분하기 어려웠습니다. Q 연계는 여러 시간 조건이 함께 돌아가므로 코드 한 부분만 읽으면 쿨타임을 잘못 이해할 수 있었습니다.

## 원인

입력·데이터·개체·전투·이동·연출이 서로 다른 클래스에 나뉘어 있고, 일부 설명은 현재 구현의 역할과 경계를 충분히 드러내지 못했습니다. Q2·Q3에 공유 쿨타임을 다시 요구하지 않는 이유와 다음 타수로 넘어가는 시점도 호출 순서를 함께 읽어야 이해할 수 있습니다.

## 해결
