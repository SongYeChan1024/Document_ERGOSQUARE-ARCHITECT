# 기획 명세서 작성 가이드

## 0. 문서 상단 메타데이터

모든 명세서는 제목 아래에 다음 정보를 둡니다.

| 항목 | 내용 |
| --- | --- |
| 문서 상태 | 기획 / 검토 요청 / 확정 |
| 우선순위 | P0 / P1 / P2 |
| 작성자 | 이름 |
| 관련 시스템 | 상대 링크 |
| 구현 상태 | 미구현 / 프로토타입 / 구현 / QA 완료 |

## 1. 필수 목차

### 0. 기획 의도

- 어떤 플레이 경험을 만들기 위한 기능인가?
- 없으면 어떤 문제가 생기는가?
- 성공 여부를 무엇으로 판단하는가?

### 1. 개요

- 기능의 한 줄 정의
- 핵심 루프에서 작동하는 시점
- 입력과 결과

### 2. 동작 규칙

- 시작 조건
- 정상 흐름
- 실패와 취소
- 예외와 경계 조건
- 멀티플레이 권한 주체

### 3. 데이터 명세

| 기획 명칭 | Key | 타입 | 기본값 | 범위·비고 |
| --- | --- | --- | --- | --- |
| 예: 전개 시간 | `deployDuration` | `float` | `1.0` | 초, 0 이상 |

### 4. UI·피드백

- 진입점
- 입력
- 화면 정보
- 성공·실패 피드백
- 접근성 고려

### 5. 연동 시스템

- 참조하는 데이터
- 발생시키는 이벤트
- 의존하는 시스템
- 순환 의존 가능성

### 6. QA 기준

- 정상 동작
- 한계값
- 동시 입력
- 연결 끊김
- 호스트 변경
- 저장·복원

### Revision History

최하단에 변경 이유와 영향을 기록합니다.

## 2. ERGOSQUARE 전용 작성 질문

새 시스템을 기획할 때 다음 질문에 답합니다.

1. 에르고스퀘어를 전개해야만 사용할 수 있는가?
2. 이 기능이 플레이어에게 제공하는 강점은 무엇인가?
3. 그 대가로 노출되는 약점은 무엇인가?
4. 팀원이 개입하거나 보호할 수 있는 지점은 어디인가?
5. 코어나 모듈이 파괴되면 어떤 기능이 중단되는가?
6. 회수·재전개로 악용할 수 있는가?
7. 네트워크에서 누가 최종 판정을 갖는가?
8. 실패 결과가 다음 설계 수정으로 연결되는가?

## 3. 작성 금지 표현

- “적당히”, “자연스럽게”, “알아서”, “상황에 따라”처럼 구현 판단이 불가능한 표현
- 근거 없이 “최적화”, “완벽한 동기화”, “지연 없음”을 보장하는 표현
- 기획값과 구현값을 구분하지 않는 수치
- MVP와 확장 범위를 섞는 서술
